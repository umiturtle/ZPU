# 他ライブラリとの違い

ZPU は「Zig で JAX の立ち位置を取る」ために、既存の選択肢と意識的に違う設計を選んでいる。
ここでは比較対象を 4 つに分けて、何を真似して何を変えたかを書く。

## 比較表

| | JAX / PyTorch / TensorFlow | NumPy | Zig エコシステム（`zig-zml`、`ndarray` 移植、手書きカーネル etc.） | **ZPU** |
| --- | --- | --- | --- | --- |
| 言語・依存 | Python + C++/XLA/CUDA | Python + BLAS | Zig、多くは C の BLAS/LAPACK に依存 | **Zig と標準ライブラリのみ**（依存ゼロ） |
| 形状 | 動的、実行時ポリモーフィズム | 動的 | 動的 or comptime | **`MAX_RANK` 次の固定ランク `Shape`** |
| メモリ | GC / deleter | GC | 手動 or アリーナ | **スコープ所有 + 明示的参照カウント** |
| 自動微分 | コンパイラ変換（XLA / autograd） | 無し | 手書き勾配が多い | **ライブラリ内の変換**（テープ + VJP/JVP 規則） |
| 変換の入れ子 | トレーサで対応 | — | — | **テープのスタックとグラフの差し替え**で対応 |
| JIT | XLA / TorchScript | — | — | **トレース計画 + 定数畳み込み**（`jit`） |
| GPU | XLA/CUDA/Metal など | BLAS | 個別に実装 | **`zbackend`: WebGPU / Metal / Vulkan / D3D12** |
| ビルド | pip / conda / コード生成 | pip | プロジェクトごと | **`zig build` だけ** |
| ドキュメント生成 | Sphinx など | Sphinx | 手書き | **リポジトリ内の Zig プログラム** |

## 1. JAX から引き継いだもの

* **関数変換という考え方。** `grad`・`jvp`・`vmap`・`jit` が「関数を取って関数を返す」
  変換であること、それらが入れ子になることは JAX の一番良いところなので、そのまま持ってきた。
* **変換は合成で作る。** `hvp` は「`grad` を `grad` で微分する」だけの実装で、
  専用のカーネルを持たない。`jit(grad(f))` も特別扱いしない。
* **イミュータブルな値 + 明示的な更新。** パラメータ更新は最適化器がその場で書き換える
  （`optim.step`）が、テンソルそのものは不変で、変換は新しいテンソルを返す。
* **乱数の明示的なシード。** `zpu.rng.Rng.init(seed)` を持ち回る（グローバルな状態は無い）。

## 2. JAX と違うところ（Zig だからという理由がはっきりしている部分）

* **形状は固定ランク。** JAX は「shape が変わったらトレースし直す」で済ませるが、
  ZPU は `MAX_RANK` 次元までの**固定ランク**として扱い、`Shape` は値型でコピーが安い。
  コンパイル時に決まる形状は `Shape.initComptime` でコンパイラに検査させ、
  実行時に決まる形状は `Shape.init` で作る。ランクの取り違えは早い段階で落ちる。
* **コンパイラを持たない。** XLA に相当するものは無く、`jit` は
  「トレースして、記録した DAG を最適化して、そのまま再生する」だけ。
  だから実行計画は読める形（`jit.Step` / `jit.Blob`）で残り、`numSteps()` で覗ける。
  そのぶん大規模カーネル融合はできない — これは意図的なトレードオフ。
* **所有権が API の一部。** Python は GC が後始末するが、Zig では誰が解放するかを
  API が決めなければならない。ZPU は「作った場所が所有する」「`Scope` がまとめて解放する」
  「変換の戻り値は呼び出し側が所有する」の 3 規則に絞り、テストで強制している。
* **スレッドは明示的。** `zpu.initThreaded(alloc, n)` で要素演算がスレッドを使う。
  既定は 1 スレッド — 計測値がぶれないようにするため。

## 3. NumPy / PyTorch と違うところ

* **GC が無い。** 中間テンソルを解放し忘れても「そのうち回収」にはならない。
  代わりに `Scope` が「この範囲の計算は使い捨て」と宣言できる。
  テストは `std.testing.allocator` で走るので、解放漏れは即失敗になる。
* **自動微分がライブラリの中にある。** PyTorch は autograd が C++ 側でテープを持つが、
  ZPU のテープ（`tape.Node`）も VJP 規則（`autodiff.contribution`）も普通の Zig の
  データ構造と関数で、`zig test` で 1 ステップずつ追える。
* **`vmap` が深さを持つ。** `batch_depth` を各テンソルが覚えているので、
  `vmap` の中で `matmul` を呼んでもバッチ軸の解釈がずれない。
  PyTorch の `vmap` 相当（functorch）は `BatchTensor` の薄いラッパを重ねるのに対し、
  ZPU はテンソル自身に深さを持たせて、演算側で 1 回だけ解決する。
* **`jit` は静的。** PyTorch の `torch.compile` はガードと再コンパイルを隠蔽するが、
  ZPU は引数の **id** が変わったときだけ再トレースする。何が起きているかは
  `j.traceCount` / `j.numSteps()` で見える。

## 4. Zig エコシステムの他の選択肢と違うところ

* **依存を増やさない。** BLAS をリンクしない、C のヘッダを要求しない。
  `matmul` は Zig で書き、ベンチで測って改善する（`bench/baseline.txt` が基準）。
* **`zgf` と層を共有する。** グラフィックで使うカーネル（ぼかし、縮小、畳み込み）と
  数値計算のカーネルは同じ `Tensor` と `ops` の上にある。微分可能レンダリングのように
  「描画を損失にする」使い方がそのまま書ける。
* **バックエンドが後付けの層。** WebGPU / Metal / Vulkan / D3D12 を
  `std.DynLib` で検出し、**実行時に選ぶ**。コンパイル時に固定しないので、
  GPU が無い環境でも同じバイナリが CPU で動く。
* **ツールチェーンが Zig で閉じる。** テスト・ベンチ・ドキュメント生成・
  バックエンド探索がすべて Zig のプログラム。CI に Python を要求しない。

## 5. まだ勝てていないところ（正直なところ）

* **絶対性能。** `matmul` は素直な実装で、単精度 512³ で約 3 GFLOP/s（本リポジトリのベンチ、
  このマシン）。BLAS を使うライブラリは桁が変わる。改善は `bench/` の数値を見ながら進める
  （タイル化と SIMD が次の作業）。
* **カーネル融合。** `conv2d` は微分可能にするため `pad` + `sliceRanges` + `matmul` の
  合成で書いており、中間テンソルが多い。融合カーネルを書けば速くなるが、
  「まず正しく、次に速く」の順で進めている。
* **演算の網羅性。** 要素演算は 60 種類以上あるが、`einsum`、`fft`、`sort`、
  スパース演算はまだ無い。
* **バックエンドの実装度。** 検出と呼び出しのインターフェースはあるが、
  各バックエンドの実カーネルは現在進行中（[マイルストーン](milestones.html) の M7）。
