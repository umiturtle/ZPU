# 2D UI ライブラリ（`zui`）

## 使い方

```zig
const zui = @import("zui");

var ui = zui.Ui.init(alloc, .{ .width = 320, .height = 200 });
defer ui.deinit();

// 画面は「今の状態の関数」として書く。ツリーを組み立てる必要も、
// コールバックを登録する必要もない。
const Body = struct {
    app: *App,

    pub fn run(self: @This(), u: *zui.Ui) zui.Ui.Error!void {
        try u.label("こんにちは, UI", .{});
        if (try u.button("click", .{})) self.app.count += 1;
        _ = try u.checkbox("enabled", &self.app.enabled, .{});
        _ = try u.slider("gain", &self.app.gain, .{ .min = 0, .max = 1 });
        _ = try u.textEdit("name", &self.app.field, .{ .placeholder = "type" });
        try u.progress(self.app.gain, .{ .w = 200 });
    }
};

// 1 フレーム = (入力, 本体)。入力は値なので、テストからもデモからも同じ関数。
const input = zui.Input{ .pointer = .{ .x = 40, .y = 12 }, .pointer_down = true, .pointer_pressed = true };
const frame = try ui.run(input, Body{ .app = &app });
if (frame.skipped) { /* 何も変わっていない: 表示リストはそのまま */ }
```

レイアウトは入れ子のコンテナで決める。`body` は `run(self, ui)` を持つ任意の型で、
**その値自身が捕捉**（Zig にはクロージャがないが、構造体のインスタンスがその代わりになる）。

```zig
const Panel = struct {
    pub fn run(_: @This(), u: *zui.Ui) zui.Ui.Error!void {
        _ = try u.button("one", .{ .w = .{ .px = 80 } });
        try u.container("fill", .{ .w = .full, .h = .{ .px = 40 }, .bg = u.theme.surface }, Spacer{});
    }
};

try ui.container("window", .{
    .w = .full, .h = .full,
    .pad = .all(12), .gap = 8, .dir = .y,
    .bg = ui.theme.bg, .radius = 8,
}, Panel{});
```

### 仮想リストとツールチップ

行数が大きい一覧は `virtualList` を使う。**見えている行だけが呼ばれる**ので、
100 万行でも 1 フレームのコストは画面に入る十数行ぶんになる。

```zig
const Rows = struct {
    pub fn run(self: @This(), u: *zui.Ui) zui.Ui.Error!void {
        try u.virtualList("log", 1_000_000, .{
            .style = .{ .w = .full, .h = .{ .px = 200 } },   // スクロール領域そのもの
            .row_height = 20,                                 // 行の高さは決め打ち
        }, self, row);
    }
    // 行は「添字」と「自分の箱」を受け取る。測られないので、背景は自分で塗る。
    fn row(_: @This(), u: *zui.Ui, i: usize, box: zui.Rect) zui.Ui.Error!void {
        try u.paintRect(box, if (i % 2 == 0) u.theme.surface else u.theme.bg);
        try u.label("row", .{});
    }
};
```

`virtualList` は `scrollable` の**代わり**（両方入れると内側がホイールを食べられる）。
高さを決め打ちにするのは妥協ではなく契約で、それによって
「目に見える範囲 = 割り算 2 回」になり、行の測定パスが消える。
行の位置は添字から直接決まる（`view.y - scroll + i * (row_height + gap)`）ので、
飛ばした行の空間を引き継ぐ事故が起きない。テストは
「100 万行でも 6 行未満しか建てない」「行間がちょうど 20 px」「ホイール 20 px で
ちょうど 20 px 動く」「見えなくなった行は建てられない」を固定している。

`tooltip` は**遅延**する: 本体の中で登録し、`endFrame` が本体のあとに描く。
だから必ず最前面に載り、コンテナや後続のウィジェットに隠されない —
ポップアップに必要な「ウィンドウ全体への 2 パス目」は要らない。
表示条件は「その id がホットかどうか」だけなので、状態も増えない。

```zig
// アンカーはホストが決める: ウィジェットは自分の箱をそのフレームの間だけ知っている。
if (textAnchor(u, "Click me")) |at| try u.tooltip(id, Rect.init(at.x - 52, at.y - 9, 104, 18), "sets clicks += 1");
```

表示リストはそのまま絵にできる。ここだけが `zgf` に依存する。

```zig
var img = try zgf.Image.init(alloc, 320, 200, 3);
defer img.deinit();
zui.render.draw(&ui.list, &img, .{ .clear = ui.theme.bg });   // scale = 2 で HiDPI
try img.savePpm(io, "frame.ppm");
```

```
zig build run-ui-demo     # スクリプト入力で 9 パネルのフィルムストリップを描く
```

## 実装意図

### 方式: 即時モード API + 保持される表示リスト + 最小の保持状態

`zui` は**ハイブリッド**を選んでいる。3 つの層で「保持するか」が違う。

| 層 | 方式 | 理由 |
| --- | --- | --- |
| ウィジェット API | **即時（immediate）** | `if` と `for` で書けた方が Zig らしい。ウィジェットツリーを状態と同期させる仕事が消える |
| フレーム（表示リスト） | **保持（retained）** | 入力が無ければ本体を走らせない、GPU に渡せる、テストが絵を見られる |
| 相互作用の状態 | **最小限だけ保持** | hot/active/focus/scroll/animation/テキスト編集 — 1 フレームの入力からは再計算できないものだけ |

**Zig の性質から方式を選んだ**部分が 3 つある。

1. **クロージャが無い。** 本体は `run(self, ui) Error!void` を持つ構造体。捕捉は
   フィールドに置くだけなので、確保も間接呼び出しも発生しない（`container(id, style, body)`
   は `body` の型で単相化される）。これが無理なら「即時モード」は書きにくい。
2. **リフレクションが無い。** ウィジェットツリーを後から走査して差分を取る設計は
   取れない。だから「ツリー」ではなく**表示リスト（命令の配列）**を保持し、
   再構築は本体を呼び直すことで行う。
3. **アロケータが明示的。** フレーム内の中間値（折り返した行、id、測定結果）は
   フレームごとにリセットするアリーナに置く。表示リストだけはフレームをまたいで
   残すので、アリーナとは別のアロケータを使う。

### 却下した代替案

| 案 | 却下した理由 |
| --- | --- |
| **完全リテインド**（ウィジェット木 + コールバック） | Zig にはクロージャが無いので、`*anyopaque` + 関数ポインタ + ユーザー側の状態構造体を手で配線することになる。木と状態の同期という、いちばん間違えやすい仕事を利用者に押し付ける |
| **完全即時（毎フレーム全再構築）** | 単純だが、入力が無いフレームでも本体とラスタライズを回し続ける。バッテリーと CPU を無駄にし、「テストで絵を比べる」こともできなくなる（毎回作り直すので差分が取れない） |
| **DSL / コード生成**（宣言的記法 + ビルド時変換） | 別の言語を覚える必要があり、エラーが読めなくなる。ビルドに外部ツールを足すことにもなる（このリポジトリは Python を要求しない方針） |
| **仮想 DOM 的な差分** | リフレクションが無いので、汎用の差分器は書けない。書けたとしても、Zig の構造体は安いので「作り直して描き直す」方が速い |
| **サードパーティ依存**（egui 風のフレームワークを移植） | 「依存ゼロ」「Zig だけで完結」という方針に反する。加えて、既存の即時モード GUI は C++/Rust のクロージャとテンプレートを前提にしている |

### 3 つの層の中身

* **表示リスト**（`frame.zig`）。命令は `rect` / `rounded` / `line` / `triangle` /
  `text` / `push_clip` / `pop_clip` の 7 種類だけ。`DisplayList` は命令の配列・
  クリップの深さ・`revision`（変わったかどうか）・`reused`（使い回したか）を持つ。
  描画命令は**すでに解決済みの絶対座標**で書かれるので、レンダラも GPU も
  レイアウトを知らなくていい。
  将来の GPU 経路のために、命令は `Instance{rect, color, radius, kind, uv}` に
  展開できる形にしてある（矩形・角丸・テキストのクアッドが同じ構造体になる）。

* **保持される状態**（`context.zig`）。`hot`（今ポインタの下にある）、`active`
  （押下を所有している）、`focus`、スクロール位置、アニメーション値、テキストの
  キャレット/選択。Id はウィジェット名と、それを包むコンテナ名の**ハッシュ**で、
  フレームをまたいで安定する。`forget` / `forgetAll` で明示的に捨てられる
  （動的なリストが縮んだときに使う）。

* **アイドル規則**。`input.isIdle()`（押下・キー・文字入力・スクロールが無い）かつ
  **ポインタが前フレームから動いていない** かつ アニメーションが動いていない かつ
  `markDirty()` されていない、なら**本体を呼ばずに表示リストをそのまま使う**。
  ポインタの位置を別に持っている理由: 位置は 2 フレームの比較でしか
  「動いた」と言えず、`isIdle()` は 1 フレームの性質だから。実測で 60 フレーム連続の
  アイドルは 1 フレームあたり 15 ns（本体の再構築は 4〜6 µs）。

### レイアウト: 2 パスと「親が決める」

`container` は本体を **2 回**呼ぶ。1 回目は測定（`measuring = true`、何も描かずに
子の希望サイズを集計）、2 回目は描画（実際の座標を配る）。`fill`（`Size.fill`）は
重み付きの残り分けで、測定パスで集めた「固定の合計」から描画パスで配分する。
`Size.auto` は内容、`Size.px` は固定、`min_w` / `min_h` は下限。位置決めは
親が全部やるので、子は自分の座標を知らなくていい（`occupy` の 1 か所に集約）。

### ラスタライザ: 形は 1 か所、経路は 2 つ

アンチエイリアスは多重サンプリングでもぼかしでもなく、**形ごとの被覆率**で作る。そして
その被覆率の計算は `src/zui/raster.zig` の `coverage(inst, x, y)` **1 関数**しかない —
ピクセル中心 `(x, y)` を渡すと 0〜1 が返る、というフラグメントシェーダと同じ形の関数である。

| 形（`Instance.Kind`） | 被覆率の出し方 |
| --- | --- |
| `rect` | ピクセル正方形との重なり面積 |
| `rounded` | 角丸ボックスの符号付き距離（SDF）→ `clamp(0.5 - d, 0, 1)` |
| `glyph` | アトラスのバイリニア補間（`uv` は `points[0..4]`） |
| `line` | 線分までの距離場、`clamp(w/2 + 0.5 - d, 0, 1)`（両端は丸キャップ） |
| `triangle` | 4×4 スーパーサンプリング（小さく稀なので、巻き方向の間違いが起きない方優先） |

**枠線は「角丸 2 枚」**。外側を枠色で、内側（`border` ぶん縮めた箱、半径 `radius - border`）を
塗り色で描く。解析的なリング（外側 SDF − 内側 SDF）を各バックエンドで再実装するより、
同じ形を 2 回並べる方がシェーダもラスタライザも 1 つの関数で済む。

描画ループも 1 か所（`raster.emit`）: インスタンスの外接矩形 ∩ クリップの範囲のピクセルを回し、
`coverage` を取って合成する。`render.zig`（表示リスト → 直接ピクセル）と
`pipeline.zig`（表示リスト → インスタンス列 → ピクセル）は、この同じループを呼ぶ。

実装で効いている細かい点が 3 つある。

* **`zgf.Image` の要素アクセサを直接使わない。** `Image` は `zpu.Tensor` なので、
  汎用の `readF64` / `writeF64` は 1 成分ごとに dtype の分岐を踏む。実測で
  **1 書き込みあたり約 80 ns**、320×200 の 1 フレームで 15 ms が形を描く前に消える。
  `Tensor.flatSliceMut(f32)`（公開 API）で **f32 のスライスをフレームに 1 回取り**、
  その中で合成する。f64 や非連続な画像は汎用経路に落ちる。これだけで
  **1 フレーム 19.5 ms → 1.9 ms**。同じ `Surface` は生の f32 バッファにも張れる
  （`Surface.fromSlice`）ので、カーネルが書く先もソフトウェアレンダラと同じコードになる。
* **`scale` は歩くときにだけ効く。** 表示リストも論理ピクセル、`Instance` も論理ピクセル、
  `Options.scale` がデバイスピクセル比。ウィジェットは DPI を知らないまま HiDPI に乗る。
* **完全被覆は「書き込み」**。アルファが 1 に達したら合成せずストアする
  （背景は 1 フレームの大半を占める）。

### フォントとアトラス

`font_data.zig` は `tools/gen_font.py` が生成した 14 px の ASCII 95 文字
（1 ピクセル 1 バイトの被覆率 + 送り幅 + インクボックス）。生成器はビルドの一部ではなく、
**生成物をコミット**する（`zig build` は Python を呼ばない）。

GPU は 95 枚のテクスチャを扱えないし、シェーダは「このグリフのバイトはどこから始まるか」を
知らない。なので `src/zui/atlas.zig` が **comptime でアトラスを組む**: 棚詰め（shelf packing）、
幅 128 texel、グリフ間に 1 texel のパディング、8 bit 被覆率の 1 枚画像。
グリフ 1 つは `uvOf(i)` の矩形になり、`rect` の箱にその `uv` を張った**テクスチャ付きクワッド
1 枚**として描ける。パディングが 0 を返すので、箱の外は `font.coverage` と同じく透明になる
（これが「経路が違っても同じ絵」の根拠の 1 つ）。

アトラスは実行時初期化も確保も無い不変の `const` 配列で、そのままアップロードできる。

生成器とリーダーの間には 2 つの不変条件がある。両方テストで固定してある。

1. **インクボックスの走査幅がそのままピクセルの歩幅**。パディング付きのビットマップを
   入れると、グリフが斜めに破れる（実際に一度そうなり、テストが捕まえた）。
   生成器は描いたピクセルの外接矩形を読み直して箱を決め、`assert` で 4 辺すべてに
   インクがあることを確かめる。
2. **未知のバイトは 1 文字ぶんの代替グリフ**。マルチバイト文字は 1 つの `?` になる
   （バイトごとに `?` が並ばない）。

### インスタンス経路: 同じフレームをデータとして描く

表示リストは**書く側の形式**（入れ子のクリップ、テキストラン）で、シェーダにそのまま渡せない。
`Instance` は**描く側の形式**で、1 形 = 1 レコード、ポインタ無し、固定長、20 float（80 バイト,
16 バイト境界に整列するのでパッキング不要）:

```zig
pub const Instance = struct {
    box: [4]f32,     // x, y, w, h（外接矩形。常に本当の外接矩形）
    color: [4]f32,
    clip: [4]f32,    // このインスタンスに効いているクリップ
    param: f32,      // rounded の半径 / line の線幅
    kind: u32,       // 0 rect, 1 rounded, 2 glyph, 3 line, 4 triangle
    points: [6]f32,  // glyph は uv、line は両端、triangle は 3 頂点
};
```

* **`zui/instances.zig` の 1 回の走査**が変換のすべて。枠線は 2 インスタンス、
  テキストは**グリフ 1 文字につき 1 インスタンス**（スペースはインクが無いので 0 枚）。
* **クリップは平坦化しない。** 各インスタンスが「その時効いていたクリップ」を持つ。
  GPU に渡す前に並べ替えても分割してもスレッドに分けても意味が変わらない。
  入れ子の復元も含めてテストで固定してある。
* **2 つの経路は同じ関数を呼ぶ。** `render.zig` と `pipeline.zig` の差は
  「歩きながら描くか、バッファに入れてから描くか」だけなので、
  「CPU と GPU で同じ絵」は願望ではなくテストになる。テストは
  1× と 2× + 原点オフセットの両方で、**画素差 0** を要求する。

デバイスに渡すものは 4 つ。`pipeline.pack`（1 インスタンス 20 float の平坦配列）、
`Params`（ユニフォーム: 枠のサイズ・原点・スケール・個数・アトラスサイズ）、
`atlasPixels()`（`r8unorm` のテクスチャ）、そして `pipeline.kernel`（カーネル本体）。

カーネルは**1 起動 = 1 インスタンス**。合成は順序依存（後の形が前を覆う）なので、
起動順を保証しないバックエンドの上では正しくない。そこで
**シェーディング言語のソースをあえて積んでいない** = `Kernel.canRun(.vulkan)` は false で、
`zbackend.dispatch` はドライバに渡して失敗するのではなく CPU に落ちる。デモはこの
「GPU では自分は走れないと申告する」ことまでテストする。

GPU 上では同じ絵を**レンダーパス**として描く: 頂点シェーダが 1 インスタンスを 1 クワッドに展開し、
フラグメントシェーダが同じ `coverage` を計算し、合成はハードウェアのブレンダに任せる。
その WGSL（`pipeline.render_pass_wgsl`）はソースとして同梱してあるが、**compute カーネルとしては
登録しない**（登録すると `canRun` が嘘になり、フラグメントシェーダを compute として
コンパイルしようとして落ちる）。

### テスト

ウィジェット層のテストはヘッドレスで、**入力の列**を流し込むだけ。`Input` は値なので、
クリックもドラッグも入力そのものの列になる。

```zig
_ = try ui.run(press(20, 13), body);
_ = try ui.run(release(20, 13), body);
try expect(clicks == 1);
```

検証は表示リスト（矩形の座標）とピクセルの両方で行う。例えば
「無効なウィジェットは入力を取らない」「アイドルフレームは本体を呼ばない」
「スクロールは両端でクランプする」「折りたたみは開閉を覚えている」
「文字入力はキャレットの位置に入る」はすべてこの形で書いてある。
`examples/ui_demo.zig` は同じ仕組みをスクリプトで動かし、9 パネルの
フィルムストリップと **31 個のチェック**を出す（`zig build run-ui-demo`）。
そのうち 6 個はインスタンス経路のもの: インスタンス数の下限、
デバイスレイアウトの往復（バイト単位で一致）、アトラスの同梱、
カーネルが GPU バックエンドを辞退すること、
**カーネルのピクセルがソフトウェアレンダラと 1 画素も違わないこと**。

## 性能（この環境、`zig build bench -- --filter ui`）

| ケース | 値 | 意味 |
| --- | --- | --- |
| フレーム再構築 320×200 | **約 4〜6 µs**（17〜23 万 fps） | レイアウト + 表示リスト生成。全ウィジェット種を含む |
| アイドルフレーム | **約 15 ns** | 本体を呼ばず表示リストを再利用 |
| ソフトウェアラスタライズ 320×200 | **約 1.27 ms**（51 Melem/s） | 角丸 SDF + テキストを含む 1 フレーム |
| 同 @2x（デバイスピクセル 2 倍） | ほぼ同じ（1.21 ms） | 見える面積が同じなので |
| 表示リスト → インスタンス列 | **654 ns** | 57 コマンド → 283 レコード（本文は 1 文字 1 枚） |
| インスタンスのパック | **232 ns** | 20 float × 283 = 22640 B を平坦配列へ |
| インスタンス経由のラスタライズ | **1.51 ms** | 歩いて、スケールして、同じループで描く |
| カーネル 1 フレーム（クリア込み） | **0.98 ms** | `zbackend` の CPU バックエンドへディスパッチ |

再構築が 1 桁マイクロ秒、ラスタライズがミリ秒 — この差が設計を決めている。
つまり **GPU に載せ替えるべきなのはラスタライザ側**で、レイアウトや状態機械は
CPU に残してよい（次のマイルストーン ZUI6）。

## 他のライブラリと違うところ

* **Dear ImGui / egui（即時モード GUI）と比べて**: API の書き味は同じだが、
  `zui` は**フレームを保持する**。入力が無ければ何もしない（15 ns）し、
  表示リストはそのまま絵になるのでヘッドレステストができる。ImGui 系は
  「描画リストを持つ」ものの、アイドル判定とテスト可能性はアプリ側の仕事になりがち。
* **Clay（C の即時モードレイアウト）と比べて**: 同じく単一ライブラリ・依存ゼロだが、
  `zui` はレイアウトだけでなく**描画と相互作用状態まで**持ち、`zgf` の画像に落とせる。
* **Slint / 宣言的 UI と比べて**: 別言語の DSL もコード生成も無い。UI は普通の Zig で、
  階層は関数呼び出しの入れ子。エラーはコンパイラが Zig のエラーとして出す。
* **HTML/CSS と比べて**: セレクタもカスケードも無い。親が子の寸法を決め、
  子は自分の座標を知らない（レイアウトは 1 か所）。
* **`zgf` との関係**: `zui` は `zgf` の**利用者**。`zui/render.zig` だけが `zgf` を
  インポートし、レイアウト・ウィジェット・状態機械は `zgf` を知らない。だから
  同じウィジェットのコードが、テスト（表示リストを見る）・画像（ソフトウェア）・
  将来の GPU（インスタンスバッファ）のどれにも使える。

## 限界（正直なところ）

* **GPU 上で走るのはまだレンダーパスではない。** カーネル経路（`zbackend`）は
  起動順を保証するバックエンドで正しく、この環境では CPU がそれにあたる。
  WGSL のレンダーパス版は同梱済みだが、**このリポジトリの CI では検証できない**
  （サンドボックスに GPU 無し）ので、コンパイルが通ることを主張していない。
  ミップマップ・テクスチャ配列・可変フォントも無い。
* **1 つのウィンドウだけ。** 複数ウィンドウ・ポップアップ・モーダルは無い。
  入れ子のコンテナとクリップで足りる範囲を想定している。
* **テキストは ASCII のみ。** フォントは 14 px の Latin 95 文字。UTF-8 は
  1 文字 = 1 代替グリフとして扱う（日本語は未対応）。
* **入力はホストが作る。** ウィンドウやイベントループは持たない
  （`Input` を渡すのはアプリの仕事）。そのぶんテストとデモが同じコードで動く。
* **選択と IME は未実装。** テキストフィールドはキャレットと挿入・削除まで。
